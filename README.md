# RuPay Benefits

A personal workspace for managing credit-card benefits and voucher inventory.

## Frontend currently in the repository

- Add credit cards with issuer, network, last four digits, benefit cycle, and benefit notes.
- Add voucher codes one at a time or in bulk (one code per line).
- Keep one brand-wise inventory across all origins: **Generated by me**, **Family cards**, and **Purchased from others**.
- Filter vouchers by brand, origin, status, and search text.
- Open any voucher to inspect its code, source, expiry, value, and provenance.
- For purchased vouchers, save the seller's name and phone number against every code in the batch.
- Track **Available**, **Sold**, and **Redeemed** separately.
- View supplier purchase history and upcoming expiries.
- Export and restore a JSON backup.

The browser UI still uses local storage. Data remains in that browser profile and does not sync to another device. Export a JSON backup before clearing browser data.

## Backend foundation

A Node.js + Express API and PostgreSQL schema are now included:
- Password sign-in using bcrypt password hashes.
- Random opaque session tokens stored as SHA-256 hashes in PostgreSQL and sent in HttpOnly cookies.
- Login rate limiting, Helmet security headers, and configurable CORS allow-list.
- User-scoped card and voucher endpoints. The API never accepts an owner ID from the browser.
- Bulk voucher insertion in a database transaction. A duplicate code rejects the whole batch.
- Seller name and phone stored on every purchased voucher row.
- Docker Compose with PostgreSQL on a private container network; the API port is bound to localhost.

**The current frontend has not yet been switched to these API endpoints.** The backend is not deployed or connected to the UI.

## Local backend setup

Requirements: Node.js 20+ and PostgreSQL 14+.

1. Copy .env.example to .env and set DATABASE_URL, APP_ORIGINS and cookie settings.
2. Install dependencies with npm install.
3. Apply the database schema with npm run migrate.
4. Create the first user from a secure shell by setting ADMIN_EMAIL and ADMIN_PASSWORD environment variables, then running npm run create-user. Use a unique password of at least 12 characters. Do not place passwords in source code or GitHub.
5. Start the API with npm start. The database health check is available at /health.

## Oracle Cloud VM deployment with Docker Compose

The included Compose file is intended for a Linux VM you control. PostgreSQL stays on an internal Docker network and the API binds to 127.0.0.1:3000.

1. Install Docker Engine and the Docker Compose plugin on the VM.
2. Clone this repository on the VM.
3. Copy .env.example to .env and replace every example value with long, unique secrets. DATABASE_URL must use the same PostgreSQL credentials and database, with Docker service hostname db.
4. Set APP_ORIGINS to the exact HTTPS origin that will host the frontend.
5. Start PostgreSQL: docker compose up -d db
6. Apply the schema: docker compose run --rm api npm run migrate
7. Create the first owner account by passing ADMIN_EMAIL and ADMIN_PASSWORD securely to a one-off docker compose run command. Do not put these values into the repository.
8. Start the API: docker compose up -d --build api
9. Configure an HTTPS reverse proxy (for example, Nginx or Caddy) to proxy to 127.0.0.1:3000. Do not expose port 5432 or the API directly over public HTTP.

Back up the PostgreSQL volume regularly and test restoring a backup.

## API endpoints

All card and voucher endpoints require a valid sign-in session cookie.

| Method | Endpoint | Purpose |
|---|---|---|
| POST | /api/auth/login | Sign in with email and password |
| POST | /api/auth/logout | Revoke current session |
| GET | /api/auth/me | Check current session |
| GET / POST | /api/cards | List or create cards |
| DELETE | /api/cards/:id | Delete a card owned by current user |
| GET | /api/vouchers | List vouchers; supports brand, source, status and q filters |
| GET | /api/vouchers/:id | View one voucher |
| POST | /api/vouchers/bulk | Add a batch of voucher codes |
| PATCH | /api/vouchers/:id/status | Change to available, sold or redeemed |
| DELETE | /api/vouchers/:id | Delete a voucher |

For bulk voucher requests, source_type is self, family or purchased. Purchased vouchers require supplier.name and supplier.phone. Family vouchers require family_member_name.

## Security notes

- Never commit .env or real database credentials.
- Do not expose PostgreSQL port 5432 publicly.
- Do not store full card numbers, CVVs, OTPs, banking passwords or payment credentials.
- Use HTTPS before enabling production sign-in cookies.
- Restrict APP_ORIGINS to the actual website origins.
- The backend must be deployed and tested, then the frontend must be integrated with it, before treating the portal as a multi-device private service.
